# Lumina P0 实时通讯可靠性设计

日期：2026-11-04  
状态：已确认，待实施

## 1. 目标与决策

本阶段把现有“可运行”的消息链路提升为断网、重连、Redis 故障和服务重启条件下仍可恢复的生产级链路，覆盖消息幂等与顺序、逐条发送状态、离线内存队列、增量同步、WebSocket 优雅关闭，以及教室端和教师端全局紧急通知。

已确认两项关键决策：

- 采用事务 Outbox 和后台 relay，保证数据库已提交的持久业务事件在 Redis 恢复后最终发布。
- 未发送队列只保存在页面内存中，不写入 localStorage、sessionStorage 或 IndexedDB。页面存在未确认发送结果时，刷新或关闭页面前必须提醒用户。

保留现有“REST 写入、PostgreSQL 事实源、Redis 实时通知”的主架构，不把消息发送迁移到 WebSocket，不引入新的重量级依赖。

## 2. 现有基础与改造边界

现有系统已经具备 BIGSERIAL 消息 ID、游标历史、通道权限、消息已读位置、逐消息已读回执、紧急确认表、Redis Pub/Sub、WebSocket 心跳、指数退避和重连后的查询失效。本阶段复用这些能力，重点补齐以下缺口：

- 发送没有客户端幂等键，响应丢失后的重试可能生成重复消息。
- 发送状态只覆盖整个表单的 pending，不具备逐条排队、失败和重试状态。
- Redis 发布失败后没有持久重试，在线且未重连的页面可能长期缺少事件。
- 已建立连接没有优雅关闭协议，服务关闭只处理 HTTP Server。
- 没有“对方已接收”回执，不能直接表达 delivered 状态。
- 紧急通知已有教室阻断和确认落库，但缺少 30 秒加强提醒、教师任意页面弹窗和发送者/管理员确认进度。

P0 不展开虚拟滚动、CSV 导入、浏览器 Notification、Wake Lock、部署备份等 P1–P3 项。

## 3. 数据模型与迁移

新增迁移必须同时提供 up/down，并保持已有数据和 API 的字符串 ID 契约。

### 3.1 消息幂等

`messages` 增加可空 `client_msg_id UUID`，并建立 `(sender_id, client_msg_id)` 的部分唯一索引，仅约束非空值。消息 DTO 返回该字段，供前端把服务端消息与本地队列项对应。

新 Web 客户端对每条逻辑消息只生成一个 UUID，所有重试复用该值。为兼容已有客户端，旧请求可以缺省该字段，但只有携带幂等键的请求获得客户端级去重保证。

同一发送者重复提交相同幂等键且请求内容一致时返回首次消息。正文、通道、类型、附件或回复目标不一致时返回 `409 IDEMPOTENCY_CONFLICT`。并发首次写入由数据库唯一索引仲裁，唯一冲突后读取并返回已提交记录。

### 3.2 投递回执

新增 `message_deliveries`：

- `message_id`：消息外键。
- `user_id`：接收用户外键。
- `delivered_at`：首次确认接收时间。
- 主键为 `(message_id, user_id)`。

客户端把消息合并到本地缓存后批量发送 delivery ACK。服务端重新校验每个通道的访问权限，忽略发送者自己的回执，以 `ON CONFLICT DO NOTHING` 写入。消息 DTO 增加非发送者 `delivery_count`，并保留非发送者 `read_count`。

发送者侧状态定义为：

- `sending`：仅存在于本地队列，正在等待或执行发送。
- `sent`：服务端已持久化，尚无接收方 delivery ACK。
- `delivered`：至少一名非发送者已确认接收。
- `read`：至少一名非发送者已读。
- `failed`：本地发送未确认成功，可手动重试；网络错误和 5xx 也可在重连后自动重试。

状态由持久化结果及回执推导，不在 `messages` 中重复保存状态枚举。

### 3.3 事务 Outbox

新增 `realtime_outbox`，至少包含：

- 自增 `id` 和全局唯一 `event_id UUID`。
- `event_type`、可空 `channel_id`、JSONB `payload` 和业务发生时间。
- `published_at`、`attempts`、`available_at`。
- `locked_at`、`locked_by`，用于多实例认领和崩溃租约恢复。
- `created_at`，用于排查和后续清理。

待发布记录按自增 ID 处理，并建立适合 `published_at IS NULL` 查询的部分索引。载荷保存事件所需业务数据，但日志不得输出载荷或消息正文。

## 4. 发送事务与 Outbox Relay

### 4.1 发送流程

单条发送按以下顺序执行：

1. 校验用户、通道写权限、消息类型、正文、回复目标和附件归属。
2. 在事务内查询幂等记录；一致则直接返回，不一致则冲突。
3. 创建消息并关联附件。
4. 使用 `GREATEST` 更新发送者的 `channel_reads.last_read_message_id`，避免并发已读位置回退。
5. 在同一事务内写入 `new_message` outbox，事件 ID 在重试期间保持不变。
6. 提交后立即返回真实消息 DTO，不等待 Redis。

编辑、撤回、紧急确认、公告和其他需要可靠跨实例分发的业务事件采用同样的事务 Outbox 边界。typing、presence 和 `server_shutdown` 等短暂事件不入 Outbox。

批量通知的新前端请求为每个目标提供独立 `client_msg_id`，服务端逐通道复用单条发送逻辑并返回逐项结果。旧 `channel_ids` 请求保持兼容，新界面不再使用无幂等键的批量路径。数据库写入完成后由 relay 异步发布，HTTP 响应不等待推送。

### 4.2 Relay 流程

Relay 以固定小批量执行以下过程：

1. 在短事务中使用 `FOR UPDATE SKIP LOCKED` 认领到期且未发布的记录，写入实例标识和租约。
2. 在数据库事务外向 Redis 发布原事件。
3. 成功后标记 `published_at`；失败则增加尝试次数、释放租约并按 capped backoff 设置下次可执行时间。
4. 崩溃实例的过期租约可被其他实例重新认领，不设置静默丢弃的最大次数。

这是 at-least-once 投递。发布成功但完成标记失败时可能重发，接收端继续按 `event_id` 去重。Relay 停止时等待当前小批量到达安全边界，再关闭 Redis 和数据库。

## 5. 增量同步与 WebSocket 生命周期

### 5.1 增量同步

增加通道级同步接口，参数为 `after_id + limit`，结果按数据库 ID 升序返回，并携带后续游标和 `has_more`。所有查询重新校验通道权限，不使用 OFFSET。

重连后的同步顺序为：活动通道、其他可见通道、未确认紧急消息、恢复发送队列。客户端优先使用本地最大服务端消息 ID；没有本地游标时使用该通道 `last_read_message_id`。返回消息与实时事件按消息 ID 去重合并，未读数据不以全局 ID 连续性推断，因为消息 ID 在全校范围内递增而非每通道连续。

WebSocket 慢连接队列溢出时主动断开，重连后补同步，不能把未写入连接队列的事件视为已投递。

### 5.2 心跳与优雅关闭

服务端协议 Ping 间隔调整为 25 秒，60 秒未收到 Pong 后断开并清理 Hub/Presence。浏览器继续使用协议 Pong，不依赖应用层 `ping` 消息保活。

`Hub.Shutdown(ctx)` 的执行边界为：停止新注册、广播 `server_shutdown`、在有界上下文中 drain 已排队事件、发送 WebSocket Close 帧、关闭连接并等待读写 goroutine 退出。主程序先停止接收新 HTTP 请求，再完成 Hub 和 relay 关闭，最后关闭 Redis 与数据库。

客户端收到 `server_shutdown` 后显示“服务维护中”；连接关闭后继续按 1、2、4、8、16、30 秒封顶的指数退避重连并加入少量抖动。普通断开显示黄色“连接已断开，正在重连…”横幅。

## 6. 前端发送队列与 UI 合并

教师端和教室端继续共用 Composer，在其前增加框架无关的每通道 FIFO 调度模块：

- 每个队列项包含 `client_msg_id`、通道、消息输入、状态和错误；附件重试复用原 `file_id`，不重复上传。
- 同一通道严格串行，不同通道可以并行。
- WebSocket 断开或浏览器离线时暂停调度；重连同步完成后按入队顺序恢复。
- 网络错误和 5xx 自动等待下一次恢复；4xx 标记失败，不盲目自动重试。
- 任何失败项均显示灰色气泡、红色感叹号和重试按钮，不静默移除。
- 存在未确认发送结果时注册 `beforeunload` 提醒；队列不持久化到浏览器磁盘。

待发送项暂列消息列表末尾，以本地入队顺序展示；REST 成功后替换为真实 DTO 并按数据库 ID 归并。图标依次为发送中、单勾、双勾、蓝色双勾；失败使用红色感叹号。已有“N 人已读”继续保留。

新消息、delivery/read 回执和队列状态进入 100ms 批处理窗口，合并为一次缓存/UI 更新。当前通道直接插入；非当前通道更新未读角标并显示应用内通知。浏览器 Notification API 留到 P2。

## 7. 全局紧急通知与确认进度

紧急通知宿主提升到已登录布局，避免仅在某个聊天页面挂载。

教室端：

- 全屏弹窗和半透明遮罩，不能通过 Escape、遮罩或关闭按钮绕过。
- 循环提示音持续到服务端确认成功；浏览器自动播放受限时保留明确的声音解锁按钮和视觉提醒。
- 30 秒未确认后闪烁加强，确认按钮高度至少 64px。
- 显示消息对应的班级/通道名称；一次只确认当前项，其余待确认项继续展示。

教师端：

- 在任意已登录页面显示全局紧急弹窗，可查看内容并跳转对应通道。
- 教师浏览弹窗不伪造教室确认记录；教室确认接口只允许教室角色调用。

复用 `message_confirmations` 和 `announcement_confirmations`。增加受权限保护的确认统计/明细接口：消息发送教师、公告发布者和管理员可查看目标班级、已确认状态和确认时间；普通教师不能查看无关通道。确认完成后发布实时事件，使同账号其他页面和确认进度视图同步更新。

## 8. 故障语义与安全约束

- 数据库事务失败时接口不返回成功，消息和 Outbox 不出现半提交状态。
- 响应丢失但事务已提交时，以相同幂等键重试返回原消息，不重复占用附件或生成紧急通知。
- Redis 不可用时 REST 消息写入继续可用，Outbox 持续重试；重连数据库同步作为客户端补偿。
- delivery、read 和紧急确认均为幂等操作；每次回执仍重新检查访问权限。
- 日志只记录请求 ID、事件 ID、事件类型、连接 ID、耗时和脱敏错误，不记录消息正文、密码、Token 或 Outbox 载荷。
- 消息正文继续按纯文本渲染，不引入 `dangerouslySetInnerHTML`。

## 9. 测试与验收

### 9.1 Go 与数据库

- 真实 PostgreSQL 验证相同/不同发送者幂等、不同载荷冲突、并发唯一约束、附件复用和事务回滚。
- 100 条并发消息及 10 用户场景验证按 ID 接收、无丢失、无重复。
- Outbox 验证业务事务原子性、Redis 故障恢复、重复事件 ID、多实例竞争和过期租约接管。
- 同步接口验证升序游标、权限隔离、已读位置不回退及回执幂等。
- Hub 验证 25 秒心跳常量、超时清理、慢连接、优雅关闭事件和 goroutine 退出。

### 9.2 Web

- 使用假 WebSocket 和计时器验证退避序列、维护状态、重连同步后再发送。
- 验证 FIFO、响应丢失重试、4xx 不自动重试、附件复用、失败按钮和刷新提醒。
- 验证消息 ID 去重排序、delivery/read 图标和 100ms 合并更新。
- 验证紧急通知任意页面弹出、30 秒加强提醒、循环音频、确认错误不关闭及班级名称。
- 验证教师/管理员确认进度权限和实时刷新。

### 9.3 真实 E2E 与完成门槛

使用真实 PostgreSQL、Redis 和三端浏览器验证：断网 5 秒恢复不丢消息、快速 10 条按序送达、100 条并发、10 用户无重复丢失、紧急通知跨页面确认，以及 Redis 故障恢复后的事件补发。

完成前必须通过：

- `go test ./...`、`go test -race ./...`、`go build ./cmd/...`。
- Web typecheck、Vitest 和生产构建；按仓库实际 npm 脚本执行，并额外检查 `pnpm` 构建可用性。
- 新增及已有 E2E 全部通过，记录基线与最终结果。

若 Docker、浏览器或网络环境阻塞，必须明确记录阻塞和未验证行为，不以单元测试替代真实 E2E 结论。
